# Multivariate Survival and Claim Frequency Modelling with Phase-Type Distributions

Bivariate modelling of (claim frequency, claim severity) on the real
**French Motor Third-Party Liability Claims** dataset (freMTPL2, 678,013
policies), using MVN-approximated copula structure, MANOVA, QDA, and
MAP/PH-inspired feature engineering, feeding a Gradient Boosting classifier
that flags high-risk policies pre-renewal — served via a risk-scoring API.

## Why this project exists

Traditional actuarial pricing treats claim frequency and severity as
independent univariate processes (a separate frequency GLM x a separate
severity GLM). This project tests that assumption directly: it fits a
bivariate normal to (log-frequency, log-severity), tests whether the
correlation is really zero, tests whether claim *behaviour* differs across
policyholder segments (MANOVA), classifies policies into risk tiers from
the joint distribution (QDA), engineers phase-type severity descriptors
per rating cell, and trains a classifier to flag policies likely to
produce a large loss before their next renewal.

## Results at a glance (real freMTPL2 data, n = 678,013 policies)

| Question | Method | Result |
|---|---|---|
| Are frequency & severity independent? | Bivariate MVN fit + correlation | **rho = +0.106** (mildly, not strongly, dependent — see REPORT.md for discussion of direction) |
| Are claimant profiles multivariate-normal? | Mahalanobis D^2 vs chi2(2), KS test | Rejected (p < 0.001) — real claims are heavier-tailed than MVN; 3.6% of claimants flagged as outliers at alpha=0.01 |
| Does claim behaviour differ by segment? | One-way MANOVA (Wilks' Lambda) | **Wilks' Lambda = 0.972, p < 0.001** — segments differ significantly |
| Can we classify risk tier from (freq, sev)? | QDA | **84.3% test accuracy** across Low/Medium/High tertiles |
| Can we flag large-loss policies pre-renewal? | Gradient Boosting + PH features | **AUC = 0.712**, PR-AUC = 0.068 (2% base rate) |

Full methodology, equations, and discussion in **REPORT.md**. All numbers
above are regenerated by `scripts/run_pipeline.py` and written to
`outputs/results/results.json` — nothing here is hand-typed.


## Setup

```bash
pip install -r requirements.txt

# Put the real data here (see "Getting the data" below), then:
python scripts/run_pipeline.py     # trains everything, writes outputs/

# Run the test suite (no pytest required, though it will also work under pytest):
python tests/test_pipeline.py
```

### Getting the data

The real dataset is already included in this package at:

```
data/raw/freMTPL2freq.csv
data/raw/freMTPL2sev.csv
```

so `python scripts/run_pipeline.py` will pick it up automatically — no
download needed. For reference, or if you need to refresh/replace these
files, the same schema is available from:
- Kaggle: `kaggle.com/datasets/karansarpal/fremtpl2-french-motor-tpl-insurance-claims`
- OpenML (no login needed): `sklearn.datasets.fetch_openml(data_id=41214)` (freq) and `data_id=41215` (sev)
- Hugging Face mirror: `huggingface.co/datasets/mabilton/fremtpl2`

`src/data_processing.py` auto-detects these files and applies the standard
cleaning steps used in the literature (Exposure clipped to 1 year, ClaimNb
clipped to 4, a known ClaimAmount==0-with-ClaimNb>=1 data artifact
corrected, ClaimAmount clipped at 200,000) before merging. **If the files
are absent, the pipeline automatically falls back to a synthetic dataset**
(`data/generate_data.py`) built with a known Gaussian-copula dependence
structure — useful for testing the pipeline or reproducing behaviour in an
offline environment, but the headline numbers above are from the real data.

## Running the API

Two servers expose the identical scoring logic (`app/scoring.py`):

**Production (FastAPI)** — the real deliverable, meant for deployment:
```bash
uvicorn app.main:app --reload --port 8000
# then visit http://localhost:8000/docs for interactive Swagger UI
```

**Demo (stdlib only, no dependencies)** — see "Why two servers" below:
```bash
python app/demo_server.py 8000
```

Both expose the same endpoints:
```bash
curl -X POST http://localhost:8000/score -H "Content-Type: application/json" -d '{
  "Area": "C", "VehPower": 7, "VehAge": 4, "DrivAge": 28, "BonusMalus": 95,
  "Density": 3200, "Region": "Rhone-Alpes", "VehGas": "Diesel",
  "VehBrand": "B4", "Exposure": 0.85
}'
# -> {"high_risk_probability": 0.76, "high_risk_flag": false, "risk_tier": "Low", ...}
```

`/score/batch` accepts `{"policies": [...]}` for multiple policies in one call.

### Why two servers?

`app/main.py` (FastAPI/uvicorn) is the intended production service — the
right tool for a real deployment (GitHub Codespaces, Docker, any ASGI
host). `app/demo_server.py` is a zero-dependency fallback built from the
Python standard library only, because the FastAPI/uvicorn packages could
not be installed in the offline sandbox this project was built in (no
network access to PyPI). It exercises the *exact same* scoring code path
(`app/scoring.py`), so it's a faithful proof that the pipeline works
end-to-end, not just a written-but-unverified API. In any environment with
internet access, prefer `app/main.py`.

## Deployment

**GitHub Codespaces** (recommended path for the "deployed app" deliverable):
1. Push this repo to GitHub.
2. Open it in a Codespace — `.devcontainer/devcontainer.json` will
   automatically `pip install`, run the data pipeline, and forward port 8000.
3. In the Codespace terminal: `uvicorn app.main:app --host 0.0.0.0 --port 8000`
4. Codespaces will prompt to open the forwarded port; append `/docs` for
   the interactive API explorer.

**Docker** (any container platform):
```bash
docker build -t risk-scoring-api .
docker run -p 8000:8000 risk-scoring-api
```

## Known limitations (see REPORT.md for full discussion)

- Real MTPL data rejects exact bivariate normality (heavy tails) —
  motivating a true copula (not just MVN) as a natural next step.
- The 5-95% correlation direction (positive, not negative) differs from
  the naive "high-frequency -> low-severity" stylized fact often cited;
  this is a genuine empirical finding on this book of business, not an
  error — discussed in REPORT.md.
- PH-inspired features are fit per rating cell (pooled across policies in
  that cell, not per-individual-policy), since a single policy rarely has
  enough claims to fit a distribution to.
- The Gradient Boosting classifier does not enforce monotonicity
  constraints on rating factors (e.g. BonusMalus); a production system
  would typically add these for auditability.
